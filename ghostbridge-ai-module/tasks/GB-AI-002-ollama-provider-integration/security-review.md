## Scope and checks performed

- Tests: `AiSecretTest`, `AiOllamaPropertiesTest`, `AiOllamaAutoConfigurationTest`, `OllamaAiProviderTest`, `OllamaCoordinatorIntegrationTest`, `OllamaLiveProviderTest`, `StubOllamaServer`.
- `.gitignore`, `.env.example`, `.kiro/specs/ghostbridge-ai/*` diffs, `.vscode/settings.json`, the GB-AI-002 task docs and `GB-AI-001 milestone.md` (gates G-M3-1 and G-M4-1).
- Context I read but did not change: `DefaultAiCoordinator`, `AiErrorReason`, `AiException`, the shared `GlobalExceptionHandler`, `GhostBridgeSecurityAutoConfiguration` (actuator rules), `rules/rules.md`, `.kiro/steering/*.md`, and the reviewer prompt including its AI module extension.

**Checks performed (code review plus throwaway probes in the session scratchpad; nothing was written to the repository except this file):**
1. **Credential flow.** I traced every `reveal()` call site. There is exactly one: `OllamaAiProvider.java:114`, which builds the `Authorization` header. I also checked string concatenation, `toString`, JSON, bind-failure text, configuration metadata, status text, exception messages, causes and logs.
2. **JDK behaviour, tested with probes against the built `target/classes` and synthetic `test-dummy-key-*` values only.** I checked:
   - how the JDK validates header values, and whether its exception text includes the value;
   - what `jdk.httpclient.HttpClient.log=headers` prints;
   - whether the client follows proxy system properties;
   - `java.net.URI` parsing of bypass candidates: `https://ollama.com@evil`, backslashes, a trailing dot, upper case, `%2e`, a Cyrillic host, `[::1]`, `:0443`, an empty port, `#@`, `:443:80`, a scheme-relative URL and surrounding whitespace;
   - gzip bodies, deeply nested JSON, and thread count per provider instance;
   - Spring bind-failure output for a URL whose user-info holds a dummy value, an invalid mode and an invalid byte limit.
3. **Destination controls:** HTTPS only, exact-match host allow-list, port, user-info, query and fragment checks, `Redirect.NEVER`, HTTP/1.1 only (so no h2 upgrade; the JDK 21 client does not honour Alt-Svc), and no custom `SSLContext` or hostname verifier.
4. **SSRF.** The endpoint comes only from validated configuration. The model id travels in the JSON body (escaped by Jackson), never in the URL.
5. **G-M3-1 limits:**
   - request size is checked in UTF-8 bytes after serialization;
   - the response is bounded by `Content-Length` and by incremental chunked reading;
   - gzip bodies are not decompressed;
   - an overall deadline covers headers and body;
   - the request is cancelled on timeout;
   - I also checked the `HttpClient` lifecycle.
6. **Status mapping and parsing:** error-status bodies are discarded, causes are dropped in `translate`, and I checked JSON robustness and token-usage sanitizing.
7. **Configuration and startup:** the `OLLAMA_API_KEY` fallback source, the eager/lazy guarantee, `@ConditionalOnProperty` behaviour, the reach of the package-private test seam, and Actuator exposure.
8. **Prompt-injection boundary (SR-9):** the system and user roles are kept separate, `max_tokens` is always forwarded, and JSON mode is used only when a schema applies.
9. **Git secret hygiene:** `git check-ignore` on 15 candidate paths, tracked-file names, hooks and CI, and whether the documents' claims are accurate.
10. **Secret pattern scan.** I ran my own regex scan over the working tree, the `git diff`, staged files, the full history (`git log --all -p`) and the `target/` build artifacts.
11. **Test run:** `mvn -o -q -pl ghostbridge-ai-module/ghostbridge-ai-core -am test`.

## Verified OK (as of this round; not a claim of absence of vulnerabilities)
- **Credential handling.** `reveal()` has a single call site (`OllamaAiProvider.java:114`, header only). The key never appears in the URL, body, VOs, status text, telemetry or the `AiRequestTelemetry` log format. `AiSecret.toString`/`@JsonValue` return `****`, `AiProperties.toString` is masked, and `hashCode` is constant. Spring bind failures for the `Ollama` record (bad URL with dummy user-info, invalid mode, invalid byte limit) printed **no** dummy value in my probes. `spring-configuration-metadata.json` lists `ghostbridge.ai.ollama.api-key` with no default. The missing-key message names settings only (`AiAutoConfiguration.java:64`, `OllamaAiProvider.java:63`).
- **Destination.** All bypass candidates I tried are rejected, either by `URISyntaxException`, by `getHost()==null`, or by the exact-match allow-list, or are refused for user-info, query or fragment:
  - `https://ollama.com@evil.com`, backslash forms, `ollama.com.`, `%2e` encoding, a Cyrillic look-alike host, `[::1]`, `https:ollama.com`, `//ollama.com`, `:443:80`, `#@ollama.com`, `?`, `#`.
  - Upper case is normalized correctly.
  - `:0443` and an empty port resolve to 443 (harmless).
- **Redirects and TLS.** `Redirect.NEVER` means a 3xx becomes `PROVIDER_FAILURE`; there is a test with a second server and a mutation check. JDK default TLS, with no trust-manager or hostname-verifier override. HTTP/1.1 only.
- **SSRF.** No caller-controlled URL reaches the client.
- **G-M3-1 is satisfied in code** (lifecycle caveat in SEC-04):
  - the request is serialized to UTF-8 bytes and rejected above the limit before any I/O;
  - the response is cut off at the limit, both for a declared `Content-Length` and incrementally for chunked bodies;
  - no `Accept-Encoding` is sent and nothing decompresses: a gzip bomb (48 KB compressed / 50 MB expanded) became `INVALID_MODEL_RESPONSE` without expansion;
  - the deadline in `future.get` covers body stalls, with `cancel(true)` on timeout;
  - `max_tokens` is always forwarded.
- **Error handling.** Error-status bodies are replaced unread. `translate` attaches no JDK cause, and malformed `Content-Length` and unexpected throwables become the generic `PROVIDER_UNAVAILABLE`.
- **Parsing robustness.** 200,000 levels of nesting give `INVALID_MODEL_RESPONSE` (Jackson `StreamReadConstraints`). NaN is rejected (Jackson default). Token counts are accepted only as non-negative `int`; huge numbers are treated as not reported, never fabricated.
- **Prompt-injection boundary (SR-9).** The trusted system prompt and untrusted user content travel as separate roles. Output is still schema-validated by the coordinator and never executed.
- **Startup.** The key is enforced eagerly even with lazy initialization. `provider=ollama` requires `model-id`, with no default model. The mock profile guard is unchanged.
- **Gates.** **G-M3-1** is addressed by this task. **G-M4-1** remains recorded as mandatory before any AI Web endpoint (`requirements.md` SR-8, `implementation.md`, `impact-analysis.md`, `GB-AI-001 milestone.md:29,42`). No web endpoint, frontend path or unauthenticated invocation path was added.
- **Supply chain.** No new dependency: JDK `HttpClient` plus the existing Jackson.

## Limitations and remaining risks
- This review was done by a Claude Code subagent applying the Kiro `ghostbridge-security-reviewer` prompt. It is **not a Kiro run**. It is a manual review plus targeted probes, not a penetration test, and no scanner was used.
- The provider is **stub-tested only**. There was no live call to Ollama Cloud, so real-world behaviour is unverified: TLS chain, actual error bodies, compression, HTTP/1.1 acceptance and usage fields.
- Probes ran on JDK 25. The project targets Java 21; header-validation and logging behaviour is the same in the 21 `java.net.http` implementation as far as I know, but I did not run them on a 21 runtime.
- The Actuator configprops masking (SEC-09) was checked by code inspection only.
- Remaining risks:
  - prompts and data go to a third-party processor;
  - prompt injection is mitigated, not prevented;
  - per-requester limits (G-M4-1) do not exist yet, so the model must not be exposed through any endpoint before M4 implements them;
  - anyone who controls the runtime configuration (`base-url` plus `allowed-hosts`) can send the key elsewhere, which is inherent to configuration trust;
  - the key lives in the heap as an immutable `String`, and each request creates a new `"Bearer " + key` string;
  - the previously shared key must be revoked at the provider by its owner (outside this repository).
- This review does not claim the code is free of vulnerabilities.

### Remaining risks (Round 2)

- Runtime controls (SEC-02 and R2-03), the hook (R2-01 and R2-02) and Actuator masking (SEC-09) are all defence in depth. Anyone who controls the JVM flags, the JDK installation, the runtime configuration (`base-url` plus `allowed-hosts`) or the logging configuration can still expose or redirect the key.
- Git protection is local and advisory until a CI or server-side control exists (R2-04).
- The Round 1 residual risks still apply:
  - prompts go to a third-party processor;
  - prompt injection is mitigated, not prevented;
  - **G-M4-1 per-requester limits remain a mandatory gate before any AI Web endpoint**;
  - the key lives in the heap as a `String`;
  - retries can be billed twice;
  - the previously shared key must be revoked by its owner, outside this repository.

### Limitations (Round 2)

- This is a Claude Code subagent applying the Kiro `ghostbridge-security-reviewer` prompt. It is **not a Kiro run**, not a penetration test, and no real scanner was used.
- The provider is **stub-tested only and was never called live**: the TLS chain, real error bodies and real header handling at Ollama Cloud are unverified.
- The Gitleaks branch was exercised only with fake binaries. The `net.properties` bypass rests on bytecode reading, not execution. `javax.net.debug` was not re-probed in Round 2.
- This review does not claim the code is free of vulnerabilities.
