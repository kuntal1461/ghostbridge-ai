# Security Review — GB-AI-003

**Reviewer:** ghostbridge-security-reviewer  **Date:** 2026-11-23  **Round:** 1

## Scope and checks performed
Read requirements.md, implementation-plan.md and the role prompt, then read the full source (main and the test inventory) of `ghostbridge-ai-module/ghostbridge-ai-web`. I also reviewed the uncommitted additive core changes (`AiException.retryAfter`, `AiLimiter`, `AiTokenBudget`, the web literals in `GhostBridgeAiLiterals`), the `GlobalExceptionHandler.statusFor` visibility change, and the shared `GhostBridgeSecurityAutoConfiguration` and `GhostBridgeWebAutoConfiguration`. For core behaviour that AI Web relies on, I read `DefaultAiCoordinator` (model resolution, input validation, metadata), `AiRequest` (requester id validation), the prompt service error messages and `AiRequestTelemetry` logging.

Areas checked:
- Authentication and authorization (shared chain, `AiAccessInterceptor`, `AiRequesterResolver`, behaviour with an application-supplied `SecurityFilterChain`).
- Requester identity and key derivation.
- The per-requester limiter (G-M4-1): bypasses, memory bound, fail-closed, concurrency, key collisions.
- G-M4-2: body limit (including chunked), UTF-8 byte limits, status/code/reason mapping, Retry-After accuracy.
- CORS, CSRF and security headers.
- Sensitive-data leakage (error bodies, status and usage endpoints, logs).
- Unknown-field rejection, the structured-schema allow-list, model and prompt abuse, usage cross-user disclosure.
- Dependencies, and coupling from ai-web to `OllamaAiProvider` or secret handling.

I ran `mvn -o -q -pl ghostbridge-ai-module/ghostbridge-ai-web test` with JDK 21. All 13 test classes passed (84 tests, 0 failures or errors). No live network calls were made.

Verified positives:
- Identity comes only from `SecurityContextHolder` (`AiRequesterResolver.java:34-41`). Anonymous, unauthenticated and blank-name principals are rejected, and the role match is exact. The interceptor (`AiAccessInterceptor.java:19`) and the controller (`AiRestController.java:45-61`) each call the resolver. Authorization therefore holds even if an application replaces the shared chain with a permissive one, because the resolver raises 401/403 independently.
- The controller, advice and auto-configuration are all gated by `@ConditionalOnAiWebSecurity` (`ghostbridge.security.enabled`, default true), so the endpoints are not registered when security is off.
- All four VOs reject unknown JSON fields through `@JsonAnySetter`, so a spoofed `requesterId` becomes a 400. `AiRestControllerTest` and `AiWebSecurityTest.aRequesterIdInTheBodyIsRejectedNotTrusted` cover this. The mapper takes `requesterKey` only from the caller argument (`AiApiMapper.java:20-27`).
- `modelId` cannot be arbitrary. The core rejects any model that is not the configured one or in `approvedModelIds` (`DefaultAiCoordinator.java:145-152`). The structured endpoint does not pass `modelId` at all. Clients cannot submit schemas, only an operator-approved identifier (`DefaultAiApiService.java:66-69`).
- Usage is filtered with `requesterKey.equals(metadata.requesterId())` (`DefaultAiApiService.java:93-95`), so no cross-user data is returned. The status endpoint performs no inference and exposes neither `AiProviderStatus.detail` nor credentials. Responses carry `Cache-Control: no-store`.
- `AiExceptionAdvice` maps configuration, credential and interruption reasons to `PROVIDER_UNAVAILABLE` with a fixed message (`AiExceptionAdvice.java:71-81`). It logs only the reason and the correlation id (`AiExceptionAdvice.java:48`).
- Retry-After is rounded up to whole seconds with a minimum of 1 (`AiExceptionAdvice.java:84-86`). It is sent only when `AiException.retryAfter` is known; a non-positive value is normalized to unknown.
- CORS and CSRF are not re-implemented in AI Web. CSRF stays on when `stateless=false` (`GhostBridgeSecurityAutoConfiguration.java:91-95`), and `AiWebStatefulCsrfTest` covers it.
- The limiter takes a single lock and bounds its map (`maxTrackedRequesters`). It refuses new requesters when full instead of evicting. It never sweeps entries with a request in flight, so an abuser's quota is not reset. Permit release is idempotent. Concurrency tests exist.
- Main source in ai-web has no reference to `OllamaAiProvider` or any Ollama type (grep over `src/main` returns nothing). It uses only the `AiProvider` SPI. Ollama appears only in two test strings, as fake provider messages. No secret handling was changed in the reviewed files; the AI Web classes do not touch credentials.
- Dependency changes in ai-web are test-scope `spring-boot-starter-test` and `spring-security-test`, with versions managed by the BOM. `spring-boot-configuration-processor` is optional. No AWS SDK was added.

## Findings
| ID | Severity (Critical/High/Medium/Low) | File:line | Issue | Impact | Remediation | Status |

| SEC-M4-01 | Medium | `AiWebAutoConfiguration.java:104`, `AiRequesterLimiter.java:64-84`, `DefaultAiApiService.java:58-60` | Cost and abuse control is request-count only (20 per minute, 2 concurrent per requester by default). There is no per-requester token or cost cap. Each request may use up to `maxOutputTokens` (the HTTP cap is 32768, the core cap applies), and the global token budget is optional (`maxTokens=0` disables it, see `AiProperties.Budget`). A few authenticated callers can therefore consume the whole global rate or budget and starve other users (LLM10). The plan lists a per-requester budget as out of scope. | Unbounded-consumption and availability risk for shared deployments. | Enable `ghostbridge.ai.budget` in production profiles and keep per-requester limits low. Track a per-requester token budget as a follow-up task. Record this as an accepted residual risk. | Open, accepted residual (documented out of scope) |
| SEC-M4-02 | Low | `AiRequestBodyLimitFilter.java:36-47`, `AiWebAutoConfiguration.java:105` | The body-limit filter is registered at `HIGHEST_PRECEDENCE + 20`, ahead of the Spring Security chain. It reads up to `maxRequestBytes + 1` (default 64 KiB) before authentication. Unauthenticated clients can get 413 instead of 401, and each in-flight unauthenticated connection can hold up to 64 KiB in heap plus a worker thread while a slow body arrives. The 413 problem response is written before the security header filters, so it lacks the security headers (for example X-Content-Type-Options). | Bounded pre-auth memory and thread amplification, bounded by the container thread pool and connection timeouts. Minor ordering inconsistency. I did not test the missing headers on 413. | Run the filter after authentication (order it after the security chain), or reject on `Content-Length` early and rely on container read timeouts. Alternatively document the bound. | Open |
| SEC-M4-03 | Low | `AiRequesterLimiter.java:107-128`, `143-152` | When the tracking table is full, every request from a new requester triggers an O(n) `sweep` and an O(n) `earliestExpiry` scan under the single global lock. `maxTrackedRequesters` can be configured up to 1,000,000. Any authenticated identity set that fills the table (or a legitimate large user base) forces repeated scans that block all other requesters. Because new requesters are rejected with 429, legitimate new users are denied until entries expire (fail-closed by design). | CPU and lock contention amplification, and denial of service for new users when the table is full. Requires many authenticated identities. | Rate-limit sweeps (for example at most one forced sweep per second), keep an expiry-ordered structure, or lower the maximum. Document that capacity must exceed the active user count. | Open |
| SEC-M4-04 | Low | `AiRequesterResolver.java:41,50-57` | The requester key is an unsalted SHA-256 of `Authentication.getName()`. The key is collision-safe and fixed-format, but low-entropy usernames (for example emails) can be recovered by dictionary attack if metadata or keys are ever exposed. `getName()` is also not scoped by issuer or tenant, so identities with the same name from different issuers or auth mechanisms share one limiter bucket and one usage view. Metadata is only in memory and the telemetry log does not print the requester id, so I found no current exposure. | Usage and quota sharing across principals that have the same name; future exposure of reversible pseudonyms. | Use HMAC with an operator secret (or include issuer or tenant in the hashed input). Document that names must be unique across auth sources. | Open |
| SEC-M4-05 | Low | `AiExceptionAdvice.java:62,41` | `SIZE_CODES` contains `"Max"`. A value that is too large for `@Max` (`maxOutputTokens` above 32768, `promptVersion` above 1000) is classified as 413 PAYLOAD_TOO_LARGE rather than 400. This is a status mismatch against the requirements table, which reserves 413 for byte size. Any one size-class error turns a mixed error set into 413. | Mapping inaccuracy only; no confidentiality impact. | Remove `"Max"` from `SIZE_CODES` (keep `Size` and `MaxUtf8Bytes`), or map by field. Add a test for out-of-range numeric options. | Open |
| SEC-M4-06 | Low | `AiExceptionAdvice.java:64-65,78-81`, `AiExceptionAdvice.java:59-61` | The advice returns `ex.getMessage()` for every reason except config, credential and interruption. Safety relies on the convention that every `AiException` message is client-safe (see the core `AiException` Javadoc). The core coordinator wraps unexpected runtime errors generically, and the Ollama provider uses fixed messages in the code I read. A future provider that throws `AiException(PROVIDER_FAILURE, <raw provider text>)` would leak through the API. Separately, validation `errors[].field` contains the caller-supplied map key text, so it reflects the caller's own input in the 400/413 body (not logged). | Potential provider-detail leak through a future provider. Self-reflection only for the field path. | For 5xx statuses, return a fixed message per reason (an allow-list) instead of `ex.getMessage()`. Truncate or sanitise the field path. | Open |
| SEC-M4-07 | Low | `DefaultAiApiService.java:44-61`, `AiGenerateRequestVO.java:22` | `POST /generate` accepts any registered prompt name. Operator control over which templates are exposed over HTTP exists only for the structured endpoint (the schema allow-list). Any `AI_USER` can invoke any current or future registered template, including templates intended for internal workflows. This matches the "registered templates only" requirement but is broader than the structured endpoint's allow-list. | Excessive agency or exposure of internal prompts to every role holder. Prompt text is not returned. | Add an optional operator allow-list of HTTP-invocable prompt names (default: deny unlisted when configured). | Open |
| SEC-M4-08 | Info | `DefaultAiApiService.java:89-101`, `AiRestController.java:53-62` | The status and usage endpoints are authenticated and role-gated but not covered by the per-requester limiter. `usage` scans up to `historyMaxEntries` retained records per call. The scan is bounded by the history size. | Low CPU cost per call; unthrottled for role holders. | Optionally apply a cheap rate limit to the GET endpoints. | Open (informational) |
| SEC-M4-09 | Info | `AiRequesterLimiter.java:73-80` | The fixed one-minute window allows up to twice the rate across a window boundary, and the limiter is local to one JVM. The Javadoc states the multi-instance limit honestly. | Burst or multi-instance multiplication of limits. | Use a distributed limiter for multi-instance deployments. | Open (documented) |
| SEC-M4-10 | Info | `GhostBridgeProperties.java:37` (`exposedHeaders` default `X-Correlation-Id`), shared CORS | `Retry-After` is not in the default exposed CORS headers, so browser clients on other origins cannot read it. The shared CORS defaults are restrictive (empty origins, credentials off). I did not change or test custom origin settings. | Frontend cannot honour Retry-After cross-origin unless the operator exposes it. | Add `Retry-After` to `exposedHeaders` in the shared defaults or document it for the frontend task. | Open |
| SEC-M4-11 | Info | `OllamaAiProvider.java:132-134` (core, read only) | The Ollama `status()` always returns ready, so the status endpoint reports `AVAILABLE` for any enabled ollama provider regardless of credential presence. This leaks no information and does not weaken the secret handling, but the status can be optimistic. | Status accuracy only. | Handle in the provider task if a stronger readiness probe is wanted. | Open (informational) |

## Missing tests
- A test with an application-supplied `SecurityFilterChain` that permits all, asserting that the resolver and interceptor still return 401 and 403 (the design claims this; I verified it by code reading only, not by a test).
- A unit test for `maxOutputTokens` above 32768 and `promptVersion` above 1000 asserting the intended status (400 per the requirements table), which would expose SEC-M4-05.
- A test that an unauthenticated oversized or chunked body yields the intended status and carries security headers (SEC-M4-02).
- A test that a limiter table full of live entries stays bounded under many new requesters, with a scan-cost or time assertion (SEC-M4-03). Existing tests cover bound and fail-closed behaviour, not cost.
- A test that proves a message from a non-config `AiException` containing provider text is not returned for 5xx statuses (SEC-M4-06). Current tests cover only the config and credential reasons.
- A test of two principals with the same name but different authority or issuer sharing a bucket (SEC-M4-04).
- A real end-to-end chunked request through the servlet container. The existing chunked test uses a mocked request with no Content-Length.

## Limitations and remaining risks
- Authentication does not exist yet (documented blocker). The endpoints deny all callers until an application plugs in a `GhostBridgeHttpSecurityCustomizer`. The security is therefore unproven against a real authentication mechanism. The gating logic is verified by tests with `spring-security-test` principals only.
- No dependency vulnerability scanner or Sonar run was performed. `mvn dependency:tree` produced no output in offline mode (plugin unavailable), so I did not independently confirm the dependency tree, the absence of cycles, or the absence of AWS SDK beyond reading `pom.xml`. I did not run `mvn clean install` or `verify` from the root.
- I did not run a live provider call, a load or concurrency stress test on a real container, or fuzz the JSON parser. The `@JsonAnySetter` unknown-field rejection was verified by existing passing tests, not by my own Jackson probing.
- Prompt injection (LLM01) and the `untrustedContent` handling are core responsibilities, reviewed under earlier tasks. Model output is returned as JSON text and must be treated as untrusted and escaped by any future frontend (LLM05). That frontend is out of scope here.
- The limiter and usage data are in memory and per JVM. Restart clears them.
- This review is not a statement that the application is free of vulnerabilities.
