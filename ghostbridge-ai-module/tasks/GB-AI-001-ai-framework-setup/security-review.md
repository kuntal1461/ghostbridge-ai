## Limitations and remaining risks
- **This review was performed by a Claude Code subagent applying the Kiro `ghostbridge-security-reviewer` prompt; it is NOT a Kiro agent run** and must not be recorded as Kiro evidence.
- **No dependency vulnerability scanner is configured or was run** (no OWASP Dependency-Check, Snyk, Trivy, etc.). No CVE status is claimed for `json-schema-validator` 1.5.7, its transitive dependencies, or anything else. **No Sonar/SAST was run.**
- Timing figures in N-01 come from one machine (JDK 25, cold JIT for the first size); the quadratic trend, not the absolute numbers, is the finding.
- Bedrock adapter (M3), web layer (M4) and frontend (M5) do not exist; authentication, authorization (`AI_USER`/`AI_ADMIN`), CORS/CSRF, HTTP body limits, TLS and credential handling, provider error mapping and output rendering (XSS) are unreviewed. Gates G-M3-1, G-M4-1 and G-M4-2 must be verified in those reviews.
- Prompt injection cannot be prevented by delimiters or sanitization. Model output must remain untrusted, schema-validated and never executed; downstream consumers (App, frontend) must escape it.
- Limiter, budget and registry are per JVM; in multi-instance deployments all limits multiply by the instance count.
- The shared `GhostBridgeProductionValidator` appears to share the lazy-initialization weakness of N-03 (same `InitializingBean` pattern); this was not tested and is outside this task's scope.
- This review does not claim the code is free of vulnerabilities.
